# Python 3.12 for the robot code

Python 3.10 support ends on 2026-10-31. Everything needed for 3.12 is in `2026-10-03-python312.patch` (apply from the repository root with `git apply docs/reports/2026-10-03-python312.patch`); nothing is applied in the tree yet.

## What the patch changes

- `workspaces/rabbit/pyproject.toml`: `requires-python = "==3.12.*"`. `uv.lock` re-resolved: the same versions (numpy 2.2.6, numba 0.68.0, llvmlite, opencv-python 4.12, pydantic), `toml` dropped by the resolver; every compiled dependency has a cp312 manylinux aarch64 wheel; `jetson-stats` and `nats-py` build from source as before.
- `docker/Dockerfile.zed`: the image keeps the Stereolabs JetPack 6.1 base (Ubuntu 22.04, system Python 3.10) and adds a uv-managed CPython 3.12.11 in `/opt/python` (`UV_PYTHON_INSTALL_DIR`, `UV_PYTHON`, `UV_PYTHON_PREFERENCE=only-managed`), so the bind-mounted `.venv` that `uv sync` creates at container start uses it. pyzed comes from Stereolabs' `pyzed-5.5-cp312-cp312-linux_aarch64.whl`, installed with `--no-deps` into `/opt/pyzed` (on `PYTHONPATH` instead of `/usr/local/lib/python3.10/dist-packages`, because `uv sync` removes packages that are not in the lock). The nanobind extension `rabbit_nvblox` is built against the same 3.12.11, and the image runs `uv sync --frozen` with `uv.lock` (now let through `.dockerignore`).
- `native/rabbit_nvblox/CMakeLists.txt`: `find_package(Python 3.12 EXACT ...)`, so a build against the wrong interpreter fails instead of producing a module the venv cannot import.

## Checked

- The whole suite under 3.12 on the Mac (`uv run --no-project --python 3.12 --with pytest --with numpy --with pydantic --with numba --with nats-py python -m pytest tests`) and on Linux arm64 in Docker with `uv sync --frozen` from the new lock (jetson-stats builds there): everything passes (130 passed, 1 skipped) except the two cases below. The two cases of `test_recovery.py::test_turning_around_in_a_corridor_needs_no_guard_stops` fail under 3.10 and 3.12 alike (1 replan where the test expects 0); they belong to uncommitted planner work in the tree, not to the Python version. `test_long_route_through_two_doors_ends_facing_the_object` failed once on a cold numba cache and passed on every rerun (timing-sensitive, as the rabbit-dev skill warns).
- The risky build steps in a plain Ubuntu 22.04 arm64 container: `uv python install 3.12.11`, a nanobind module built with `find_package(Python 3.12 EXACT)` against it and imported from a 3.12 venv, and the pyzed cp312 wheel installed into `/opt/pyzed` (`pyzed/sl.cpython-312-aarch64-linux-gnu.so`). The full image (CUDA, nvblox) was not built: that takes about 15 minutes on the Jetson or a CUDA-capable arm64 builder.

## Numba and behaviour

- Same numba 0.68.0 and the same warnings: `NumbaWarning: Code running in object mode won't allow parallel execution despite nogil=True` at the `objmode` deadline check in `lib/planner.py` (present under 3.10 too, harmless: the object-mode block runs every 256 expansions). Under 3.10 the suite also printed 60+ `DeprecationWarning: There is no current event loop` from `tests/sim.py`; 3.12 does not, but `asyncio.get_event_loop()` without a running loop still has to go before 3.14.
- The numba cache in `__pycache__` is per Python version, so the first start after the switch recompiles the planner kernels (about 30 s cold on the Jetson, as after a code change).
- CPU: the closed-loop simulator tests (Python control loops plus numba planning) took 17.2 s of CPU under 3.12 against 19.0 s under 3.10 on the Mac, about 10 % less. Expect 5–10 % less CPU for the Python parts of nav, planner, explore and the small nodes; the SDK-bound share of `rabbit-zed` does not change.

## Rollout

1. Apply the patch, build the `rabbit` image on the robot (`scripts/deploy.sh --build rabbit-zed`), about 15 minutes for the native stage.
2. Every `rabbit-*` container runs `uv sync` at start on the same bind-mounted `.venv`, which must be recreated for 3.12 once. Run it once before the nodes restart, so they do not recreate it concurrently: `docker compose run --rm --no-deps rabbit-nav uv sync`.
3. Do not apply only the `pyproject.toml`/`uv.lock` part: on the old image `uv sync` would download a 3.12 interpreter on its own, and the 3.10 pyzed and `rabbit_nvblox` would no longer import.
4. `docker/Dockerfile.loc` (rabbit-loc, in progress by another agent) still builds a Python 3.10 venv and its own nanobind module; it needs the same change.
